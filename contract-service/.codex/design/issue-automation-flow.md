# Issue 기반 자동화 에이전트 흐름 요약 (초안)

## 목적
- 사용자가 직접 작성한 GitHub Issue를 기준으로 코드 작성, 리뷰, QA, PR 생성까지 자동화된 프로세스를 구성한다.
- 단순 프롬프트보다 다단계 실행, 도구 호출, 검증 루프가 필요한 작업을 에이전트화하고, LangGraph 같은 상태기계로 흐름을 관리한다.

## 현재 합의된 흐름(요약)
1. 사용자가 Issue를 직접 작성한다.
2. Codex에서 Issue 내용을 기반으로 Code Agent가 구현한다.
3. Code Agent는 코드 전체가 아니라 메타데이터(클래스/메서드/변수 이름 등)를 Review Agent에게 전달한다.
4. Review Agent가 품질을 확인하고 피드백 또는 OK를 반환한다.
5. 피드백이 있으면 Code Agent가 수정 후 재검토를 반복한다. OK이면 QA Agent로 전달한다.
6. QA Agent가 테스트 코드 작성 및 E2E 테스트까지 수행한다(엣지 케이스 포함).
7. QA에서 문제 발견 시 Code Agent로 피드백하고 2번부터 재진행한다.
8. 정상이라면 PR Agent가 커밋을 정리하고 PR 템플릿에 맞춰 생성한다.

## 개선 요약(결정 사항)
- Review Agent 전달물은 최소 메타데이터(변경 요약/파일/리스크/테스트 계획/핵심 diff)로 통일.
- E2E는 기본 비활성, 라벨 또는 중요도 기준으로 선택 실행.
- 반복 루프 종료 조건은 “Review OK + QA OK + 테스트 통과”.

## 추가 고려 사항(보안/장애/운영)
### 보안 및 권한
- 최소 권한 원칙: GitHub/Notion/MCP 등은 필요한 범위만 토큰 권한 부여.
- 민감정보 마스킹: 로그/환경변수/API 키/개인정보를 에이전트 입력에서 자동 마스킹.
- PR/코드 노출 범위 제한: 외부 LLM에 전송되는 데이터의 범위를 규정.
- 감사 로그: 에이전트가 수행한 도구 호출 기록을 남겨 추적 가능하도록 한다.

### 무한 루프/과도 반복 방지
- 루프 상한선 설정: 동일 이슈의 수정-리뷰-재수정 반복 횟수 제한.
- 실패 원인 분류: 반복 실패 시 “원인 유형(설계/테스트/요구 불명확)”을 분리해 재진입 경로 다르게.
- 수동 개입 조건 정의: N회 실패 시 사람 리뷰/결정으로 전환.

### 비용/토큰 관리
- 단계별 토큰 상한 지정 및 대용량 파일/로그 요약 규칙.
- E2E는 기본 비활성, 중요 라벨에서만 활성화.
- 로그 분석은 최근 N개 또는 N라인 제한.

### 품질 리스크
- 리뷰 에이전트가 코드 전체를 보지 못하면 품질 진단이 부정확해질 수 있음.
- 중요한 보안/성능 이슈는 메타데이터만으로 탐지하기 어렵다.
- 해결 방안: 위험도가 높은 이슈에는 “부분 코드 스니펫” 또는 “파일 단위 허용” 옵션 제공.

### 테스트 불안정성
- QA 단계에서 테스트 flakiness(비결정성) 대응 필요.
- 재시도 정책, 테스트 격리, seed 고정 등의 룰을 지정.

### 권한/환경 문제
- CI 환경/로컬 환경 차이로 테스트 실패 가능.
- 테스트 실행 환경을 고정하거나 컨테이너 기반으로 표준화 필요.

### 운영 실패 시나리오
- 도구 호출 실패(GitHub API, Notion MCP) 시 재시도 및 대체 경로 필요.
- PR 생성 실패 시 변경 사항과 결과를 임시 저장/보고해야 한다.

## 에이전트 간 전달 원칙
- 메타데이터 중심 전달로 토큰 사용을 최소화한다.
- 위험도가 높은 이슈에만 제한 스니펫 또는 파일 단위 공유를 허용한다.
- 각 에이전트는 불명확한 경우 질문을 생성하고, 상위 흐름에서 사용자 결정을 받는다.
